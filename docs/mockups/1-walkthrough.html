Interface mockups

What a developer sees when they use Counterexample

The main tool runs in your terminal. You type a few commands and it does the work. A web dashboard shows the same results with better visuals. These screens use the demo shop app as the example.

You type or approve Bob reads and reasons Engine runs and proves

Step 5
YouBob

Ask Bob why it broke

Run cx explain 001. Bob gets the rule, the 3 steps, the logs and the code. It points to the exact line and proposes a fix. You decide whether to apply it.

~/shop-app $ cx explain 001

  Each refund is checked alone against the order total.
  Earlier refunds on the same order are ignored.

  + already = sum(r.amount for r in order.refunds)

The whole flow

  1. cx init in a folder, or connect a GitHub repo: Bob reads the project, starts it in Docker and proposes rules.
  2. You approve the rules. They're saved as code in your repo.
  3. cx run: the engine tries thousands of sequences and finds a broken rule.
  4. The engine shrinks the failure to the smallest sequence and saves it as a test.
  5. cx explain: Bob finds the root cause and proposes a fix.
  6. cx verify: the engine replays the steps and searches again to prove the fix. For GitHub repos, the fix arrives as a pull request.
  7. CI runs it on every pull request after that.
